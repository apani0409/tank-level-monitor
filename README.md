# Tank Level Monitor

A dashboard for IoT tank-level monitoring: level history, consumption analytics,
two complementary leak detectors, sensor-health tracking, and an operations event log.

**Live demo:** https://tank-level-monitor.vercel.app

## Why this exists

Built after reading about [Element System](https://www.elementsystem.com)'s work
automating water infrastructure in Costa Rica — ultrasonic sensors on storage tanks,
remote monitoring, and the Nandayure aqueduct project that cut water loss 15-20% for
1,300 households. This is a demonstration of that pattern: sensor readings in,
actionable decisions out.

**Honest framing:** the sensor data is synthetic, generated by
[`scripts/generate-data.ts`](scripts/generate-data.ts). There is no real hardware or
client data behind this. What it is meant to show is how I'd approach the problem —
particularly the parts that only surface once you take the measurement seriously.

## What it does

### Two leak detectors, for two different failure modes

Neither detector is redundant, and the demo dataset is built to prove it:

| Detector | Catches | Misses |
|---|---|---|
| **24h rate vs. baseline** — recent consumption more than 1.8× the tank's own historical median, sustained | Sudden bursts | Slow seepage, which raises the baseline as it goes |
| **Minimum night flow (MNF)** — net level drop between 02:00 and 04:00, averaged over the last 7 nights | Persistent low-level loss | Bursts younger than a night or two |

In the shipped data, *Tanque Industrial A* has a burst the rate rule catches while MNF
has not yet reacted, and *Tanque Comunal Sur* has a slow seepage that MNF flags and the
rate rule never sees. Both cases are locked in by tests.

MNF is the standard technique water utilities use: between 02:00 and 04:00 legitimate
demand is near zero, so most of what still moves is loss.

### Consumption analytics

Hour-of-day demand profile (with the night window highlighted), consumption by weekday,
week-over-week trend, and an expected-vs-actual overlay that compares recent hours
against the tank's own historical profile — which is what makes a leak alert legible
rather than just a threshold that tripped.

### Sensor health

Field sensors fail in specific ways, and each one is injected into a different tank:
a frozen sensor repeating one value, a 14-hour communications dropout, physically
impossible readings, and a sensor that goes silent. Invalid readings are dropped before
any analysis runs — a glitch should not be able to fake a leak or hide one.

### Event log

Refills, threshold crossings, leak suspicions and sensor faults as a chronological
list. A chart shows what happened; a log is what gets pasted into a ticket.

## Two things the tests caught

Worth writing down, because both were real and neither was visible from the UI:

1. **The MNF thresholds flagged healthy tanks.** Overnight demand sits *below* the
   sensor's noise floor. Summing hour-to-hour decreases counts every downward noise
   blip as consumption while ignoring the upward ones, which biased night flow upward
   by roughly 3×. Fixed by measuring the *net* level change across the night window so
   symmetric noise cancels — which is also how utilities actually measure it.

2. **A leak can contaminate its own baseline.** The first version compared recent
   consumption against a median computed over all history, including the leak. A slow
   leak quietly became the new normal and the alert never fired. The baseline now
   excludes the recent window.

## Stack

React 19 + TypeScript + Vite, Plotly.js for charts, Vitest for tests. Fully
client-side — no backend, data is a static JSON file.

## Running locally

```bash
bun install
bun run scripts/generate-data.ts   # regenerates public/tanks.json
bun run dev
```

## Tests

```bash
bun run vitest run
```

42 tests: unit tests over hand-built fixtures for the detection rules, consumption
aggregation and sensor-health checks, plus regression tests asserting that the shipped
dataset genuinely demonstrates what this README claims it does.
